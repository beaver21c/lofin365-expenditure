# 설계 근거와 현재 상태

무엇을 왜 이렇게 만들었는지, 그리고 **아직 확인되지 않은 것이 무엇인지** 적는다.
추정으로 채워 넣은 값은 없다. 확인되지 않은 것은 확인되지 않았다고 표시한다.

---

## 1. 왜 수집과 빌드를 나눴나

원자료를 만드는 워크플로와 대시보드를 만드는 워크플로가 따로 있다.

이 분리로 얻는 것이 하나 있는데, 그게 결정적이다.
**집계 방식을 바꿀 때 API 를 다시 호출하지 않아도 된다.**
집계 단위를 바꾸거나 검색 색인 구조를 손볼 때마다 수십 분씩 재수집하는 것과,
이미 받아 둔 원자료로 빌드만 다시 도는 것은 개발 속도가 완전히 다르다.

부수적으로 따라오는 것들:

- 브라우저가 API 를 직접 부르지 않으므로 **교차출처(CORS) 문제가 없다**
- **API 키가 브라우저에 들어가지 않는다.** 수집 워크플로의 Secrets 에만 있다
- 사용자는 기다리지 않는다. 화면을 열면 이미 집계된 결과가 있다

### 실시간 조회를 하지 않은 이유

이 API 는 **세부사업 단위 원자료**를 준다. 집계 엔드포인트가 아니다.
1개 연도 전국이 약 47만 행이고 한 번에 980행씩 받으므로 연간 약 482회 호출이 필요하다.
브라우저에서 10년치를 받으면 4,800여 회, 수십 분이 걸린다. 대시보드로 쓸 수 없다.

## 2. 저장 위치를 셋으로 나눈 이유

| 무엇 | 어디에 | 근거 |
|---|---|---|
| 코드 | git 저장소 | 수백 KB. 영원히 늘지 않는다 |
| 원자료 CSV | 비공개 저장소의 Releases | **연도당 87~129MB (실측).** 2018년 103.5MB, 2025년 128.6MB 는 GitHub 의 파일당 100MB 한도를 넘어 git 에 넣을 수 없다. Releases 는 파일당 2GB 이고 git 이력에 들어가지 않는다 |
| 대시보드 데이터 | Actions 아티팩트 → Pages | 커밋하지 않는다 |

### 대시보드 데이터를 커밋하지 않는 이유

검색용 세부사업 데이터를 포함하면 빌드 산출물이 수십 MB가 된다.
이걸 매 빌드마다 커밋하면 **git 이 모든 버전을 영구 보관한다.**
JSON 은 델타 압축도 잘 먹지 않아서, 집계를 손볼 때마다 저장소가 불어나고
**한 번 커밋된 이력은 히스토리를 다시 쓰지 않는 한 줄일 수 없다.**

Actions 아티팩트로 배포하면 저장소에는 코드만 남는다.
배포가 통째로 교체되므로 매니페스트와 데이터가 어긋난 중간 상태도 생기지 않는다.

### 외부 클라우드를 쓰지 않은 이유

R2·S3 같은 것을 붙이면 자격증명이 하나 늘고 개인 명의 과금이 인프라에 묶인다.
얻는 것은 없다 — 여기서 필요한 일은 GitHub Releases 가 이미 다 한다.
파일이 2GB를 넘거나 GitHub 밖 협업자와 원자료를 공유해야 할 때 다시 검토한다.

### 저장소 간 연결을 pull 방향으로 한 이유

`deploy-pages` 는 **자기 저장소의 Pages 에만** 배포한다. 크로스 저장소 배포가 없다.
그래서 방향이 사실상 결정된다.

- **pull(공개 ← 비공개)**: 공개 저장소 워크플로 하나로 끝난다.
  받기 → 집계 → 배포. 커밋 없음, 원자적 배포
- **push(비공개 → 공개)**: 공개 저장소 브랜치에 커밋하거나(위의 이력 누적 문제가
  그대로 돌아온다) 다른 워크플로를 깨워야 한다(결국 pull 이 한 단계 늘어난 꼴)

부수적으로 공개 저장소의 Actions 는 무료·무제한이라 빌드를 여러 번 돌려도 부담이 없다.

## 3. 계산에서 조심한 것

그래프는 멀쩡해 보이는데 값만 틀리는 종류의 오류가 있다. 아래 셋이 그렇다.

### 3.1 비중(%)의 분모

기본은 **한 단계 위**다. 추이 화면이 이 규칙을 쓴다.

- 분야(080, 090)를 고르면 → 분모는 **전 분야 세출 총액**
- 부문(081, 082…)을 고르면 → 분모는 **상위 분야 총액**

구성·지도 화면은 분모를 **사용자가 고른다**(`LF.series` 의 `sel.denFields`).
기초생활보장(081)은 전체 세출의 26%이면서 동시에 사회복지의 29%다.
둘 다 맞는 값이고 묻는 것이 다르므로, 하나만 낼 수 있게 하면 절반은 못 묻는다.

고를 수 있는 분모는 전체 세출 / 080 / 090 / 080+090 네 가지다. 코드에 적지 않고
`M.focus_fields` 에서 만들므로 집계 대상 분야가 바뀌면 목록이 따라간다.
**고른 분모는 제목·설명·엑셀 조건표에 그대로 적는다.** 화면 문구와 실제
나눗셈이 어긋나면 인용된 숫자가 조용히 틀리게 된다.

여기서 집계 순서가 정해진다. `aggregate.py` 는 **080·090 으로 거르기 전에**
전 분야 총액을 먼저 집계한다. 순서를 바꾸면 분모가 데이터에서 사라져
퍼센트 전환 기능이 통째로 불가능해진다.

같은 이유로 조회에 분야 필터를 걸지 않는다. 자치단체 단위로 전 분야를 받으면
분모가 따라온다.

### 3.2 분위 밴드는 비율의 분포

%로 볼 때, 시도 분포는 **지자체별 비율을 먼저 구하고 그 분포의 분위수**여야 한다.

```
틀림   Q1(시군구별 080 합계) / Q1(시군구별 총액)
맞음   Q1(시군구별 [080 ÷ 그 지자체 총액])
```

합계끼리 나누면 분포가 아니라 시도 평균 하나가 나온다.
절대액 모드와 % 모드에서 밴드를 **각각 따로** 계산한다 (`core.js` 의 `LF.band`).

### 3.3 모집단에서 빼야 하는 것, 표본이 부족한 곳

- **광역 본청 제외.** 도 본청 예산은 시군구와 성격이 달라 한 분포에 넣으면
  분위가 통째로 왜곡된다. 자치단체명 접미(`…본청`)와 광역 코드 일치로 판별한다
- **표본 5곳 미만이면 밴드를 그리지 않는다.** 세종·제주는 기초자치단체가 아예 없다
  (제주시·서귀포시는 행정시라 예산이 도로 편성된다). 숫자는 나오지만 의미가 없으므로,
  밴드를 숨기고 사유를 화면에 적는다
- **그 해에 없는 지자체는 분위 계산에서 뺀다.** 0으로 채우지 않는다

### 3.4 그 밖에

- **사업 수는 세부사업 코드 기준 고유 개수.** 같은 사업이 회계·부문별로 여러 행에
  나타나므로 행 수를 그대로 세면 부풀려진다. 선택 지자체의 세부사업 파일에서
  세므로 어떤 필터 조합에서도 정확하다
- **결측 연도는 선을 끊는다.** "예산이 0"과 "데이터가 없음"은 다르다.
  화면에 그 사실을 적는다
- **분모가 0이면 0%가 아니라 빈칸.** 0%는 "예산이 없다"로 읽히지만
  실제로는 "계산할 수 없다"이다
- **코드는 문자열로만 다룬다.** 분야 코드 `"080"` 을 숫자로 바꾸면 `80` 이 되어
  비교가 전부 실패한다. 세부사업 코드는 16자리라 숫자로 읽으면 손상된다
- **금액은 정수로 변환한다.** 코드 컬럼과 같은 규칙(문자열)을 금액에 적용하면
  합계가 문자열 이어붙이기가 된다. 조용히 틀리는 종류라 특히 조심한다

## 4. 검색을 지자체 범위로 한 이유

키워드 검색은 본질적으로 **행 단위 사업명 텍스트**가 브라우저에 있어야 한다.
전국을 한 파일로 만들면 100만 행이 넘어 불가능하다.

선택한 시군구 안에서만 검색하면 파일 하나만 받으면 되고,
추이·구성 탭에서 이미 받아 둔 것을 그대로 쓰므로 **추가 요청이 없다.**

크기를 줄이는 데 두 가지를 썼다.

- **사업명 사전 인코딩** — 같은 사업이 해마다 같은 이름으로 반복되므로,
  고유 이름만 배열로 두고 행에는 색인 정수만 넣는다
- **사업코드 정수화** — 16자리 문자열을 파일 안에서만 통하는 작은 정수로 바꾼다

부수 효과로 **검색이 빨라진다.** 수천 행 대신 수백 건짜리 사전만 훑으면 된다.

공백 제거 사본은 저장하지 않고 브라우저가 읽을 때 만든다.
"노인 일자리"와 "노인일자리"가 섞여 있어 정규화가 필요한데,
사전이 작아서 그때 만드는 편이 낫고 원본과 어긋날 여지도 없앤다.

## 5. 지도가 그리는 단위

지도의 한 면은 경계 도형 하나가 아니라 **예산이 편성되는 자치단체 하나**다.
둘이 어긋나는 곳이 양쪽으로 있다.

**경계가 더 잘게 나뉜 곳 — 일반구.** 경계 데이터는 용인시를 처인·기흥·수지구로
나눠 담지만 지방재정365의 자치단체는 용인시 하나다. 크로스워크(`build_geo.py`)가
`merged_cities` 로 세 코드를 한 자치단체에 묶고, 렌더러(`map.js`)가 그 묶음을
**한 면·한 값·한 이름**으로 그린다. 묶지 않으면 같은 값이 세 번 칠해지고
이름표도 세 번 붙어, 용인시가 세 지역인 것처럼 읽힌다.

안쪽 구 경계선은 지운다. 도형을 실제로 합치는 계산 대신 TopoJSON 의 호(arc)를
쓴다 — 맞닿은 두 도형은 같은 호를 공유하므로, **한 묶음 안에서 두 번 나오는
호가 곧 안쪽 경계**다. 그것만 빼고 그리면 바깥 테두리가 남는다.

**재정이 더 굵게 잡히는 곳 — 단층제.** 세종·제주는 기초자치단체가 없다.
그대로 두면 제주시·서귀포시가 영원히 회색으로 남는다. 기초가 **하나도 없는**
시도에 한해 본청을 시도 경계 전체에 잇고(`single_tier`), 지도에 그 값을 올린다.
기초가 있는데 이름을 못 맞춘 경우까지 본청으로 덮으면 결합 실패가 지도에서
사라져 버리므로, 그런 곳은 미매칭으로 남겨 경고에 잡히게 한다.

다른 시도의 본청은 지도에 올리지 않는다. 시군구와 별개 예산이라 겹쳐 칠할 면이
없다. 그래서 **지도에 칠해진 값의 합은 그 시도의 총액이 아니다.** 화면 아래
설명에 이 사실을 적는다.

### 5.1 확대를 넣은 이유

전국 지도는 240여 개 면이 들어간다. 축소 상태에서 이름을 다 띄우면 겹쳐서
읽히지 않고, 자리가 되는 곳만 띄우면 넓은 군 몇 곳(강원·경북)만 이름이 붙어
**그 지역만 강조한 그림**이 된다. 그래서 전국에서는 일정 배율 아래로 이름을
아예 띄우지 않고, 확대해 자리가 생기는 만큼 나타나게 했다.

구현에서 나뉘는 지점이 하나 있다. 도형은 `<g>` 하나에 담아 `transform` 으로
옮기고 키운다 — 다시 그리지 않으므로 휠을 굴려도 끊기지 않는다. 반면 **글자는
확대에 딸려 커지면 안 되므로** 변환 밖 층에 두고, 배율이 바뀔 때마다 자리를
다시 계산한다. 넓어진 면에 새 이름이 들어가는 것도 이 재계산에서 일어난다.
선 굵기도 배율로 나눠 화면 기준으로 일정하게 유지한다 — 확대했다고 경계선이
굵어지면 좁은 자치구가 선에 먹힌다.

## 6. 확인되지 않은 것

| 항목 | 상태 | 영향 |
|---|---|---|
| **예산 기준 명칭** | 미확인 | 당초예산/최종예산/예산현액 중 무엇인지 확인되지 않았다. 다만 10년 내내 같은 API·같은 기준일(12/31)이라 **시계열 내부 일관성은 있다.** 화면과 엑셀에는 확인된 사실(출처·기준일)만 적는다 |
| **`cpl_amt` 의 의미** | 미확인 | 총액보다 큰 값이 관측됐다는 기록만 있다. **어느 지표에도 쓰지 않으므로** 집계에서 아예 읽지 않는다 |
| **재원 4항목 = 총액** | 검산 대상 | 국비/시도비/시군구비/기타의 의미는 값 패턴에 근거한 추정이다. 집계할 때마다 전량 검산해 불일치율을 매니페스트에 남긴다. 1%를 넘으면 경고를 띄운다 |
| **부문 코드 목록** | 데이터에서 추출 | 081~086 / 091~093 같은 목록을 미리 적지 않았다. 매니페스트가 원자료에서 뽑은 값을 그대로 담고 화면은 그것을 따른다 |
| **연도별 실제 완전성** | 측정으로 확인 | 수집기가 완전성 0.99 이상을 '완전'으로 기록해서 최대 1%까지 누락이 숨어 있을 수 있다. `progress.json` 의 수집 건수와 전체 건수를 대조해 매니페스트에 싣고 화면 하단에 표시한다 |
| **자치단체 유형 분류** | 이름 기반 추정 | 자치단체명 접미(시/군/구)로 나눈다. 별도 마스터가 없어 정확한 행정 분류와 다를 수 있다 |

### 범위에서 뺀 것

- **1인당 예산 / 인구 결합** — 인구자료가 없고, 요구된 세 기능에 필요하지 않다.
  없는 분모를 추정값으로 대체하지 않는다
- **전국 범위 검색** — 위 4의 이유. 나중에 전국 사업명 사전을 따로 만들어
  "어느 지자체에 이 사업이 있는지"까지 보여주는 확장 여지는 남아 있다

## 7. 해석할 때 조심할 것

- **사업 수 증가가 곧 서비스 확대는 아니다.** 사업 분할·통합 효과가 섞이므로
  사업당 평균예산과 함께 본다. 화면에도 같이 표시한다
- **행정구역 개편이 시계열을 끊는다.** 자치단체 코드가 바뀌면 이전 연도와
  연결되지 않는다. 매니페스트에 지자체별 존재 연도를 담아 결측으로 처리한다
- **광역과 기초를 단순 합산하면 안 된다.** 시도비 보조금이 기초 세출에
  재계상되므로 중복이 생긴다
- **명목액이다.** 10년 시계열의 증가에는 물가 상승분이 포함되어 있다
- **회계 범위에 따라 총액이 크게 달라진다.** 현재 범위를 화면과 엑셀에 항상 적는다

## 8. 파일별 역할

| 파일 | 하는 일 |
|---|---|
| `scripts/lofin_common.py` | 비공개 저장소 접근, 토큰 확인, CSV 로딩과 dtype 처리 |
| `scripts/measure.py` | 1단계 측정. 추정치를 실측값으로 바꾸고 보고서를 만든다 |
| `scripts/aggregate.py` | 2단계 집계. 연도별 순차 처리 → `_site/` 생성 |
| `scripts/build_geo.py` | 경계 데이터와 지방재정365를 이름으로 결합. 일반구 묶기, 단층제 처리 |
| `scripts/make_fixture.py` | 합성 데이터로 `_site/` 생성. 원자료 없이 화면 확인용 |
| `web/core.js` | 적재·집계·분위수·단위 환산. 계산은 전부 여기 |
| `web/app.js` | 화면과 조작. 선택지는 매니페스트에서 만든다 |
| `web/map.js` | 코로플레스 지도. TopoJSON 디코딩, 자치단체 묶기, 확대·이동 |
| `web/export.js` | 엑셀 쓰기(직접 구현)와 이미지 저장 |

### 엑셀 라이브러리를 쓰지 않은 이유

필요한 것이 '쓰기'뿐인데 흔히 쓰는 라이브러리는 900KB에 파싱 쪽 취약점 이력이 있다.
읽지도 않을 코드를 사용자 브라우저에 올릴 이유가 없다.
xlsx 는 XML 몇 장을 zip 으로 묶은 형식이고 zip 은 무압축 방식이 규격상 유효하므로
압축 알고리즘 없이 만들 수 있다. 생성된 파일은 zip 무결성과
표준 라이브러리 읽기로 검증했다.

## 9. 데이터 형식

### `data/manifest.json`

대시보드가 가장 먼저 읽는다. **화면의 모든 선택지가 여기서 나온다.**
연도 목록, 자치단체와 각각의 존재 연도, 시도별 시군구 수, 분야·부문·회계 코드,
수집 완전성, 검증 결과, 경고가 들어 있다.

연도나 지역을 코드에 적지 않았으므로, 수집된 원자료가 늘거나 줄면
화면이 저절로 따라간다.

### `data/agg/{시도}.json`

행 객체가 아니라 **컬럼별 배열**로 저장한다. 같은 값이 길게 반복되는 구조라
이 형태가 훨씬 작고 gzip 전송에서도 유리하다.

- `tot` — 전 분야 총액. 퍼센트의 분모
- `det` — 080·090 부문별 상세. 재원 분해와 집행액 포함

### `data/biz/{지자체}.json`

세부사업. 사업명·사업코드를 사전으로 분리하고 행에는 색인만 둔다.
선택한 지자체 하나만 받는다.

### `data/geo/crosswalk.json`

경계 코드와 재정 코드를 잇는 표. 두 체계는 값이 겹치면서 뜻이 달라
(`26` 이 경계에서는 울산, 지방재정365에서는 부산) 숫자로 이으면
**오류 없이 엉뚱한 지역에 색이 칠해진다.** 그래서 이름으로 잇고 결과를 남긴다.

- `region[자치단체코드]` — `{sido, sgg: [...], nm}`. `sgg` 가 여러 개면 일반구를
  묶은 것이고, `single: true` 면 단층제라 시도 전역을 덮는다
- `single_tier` — 기초자치단체가 없어 본청을 올린 시도의 자치단체 코드
- `match` — 매칭률, 못 맞춘 자치단체, 재정 데이터가 없는 경계.
  매칭률이 95% 아래면 `available: false` 로 지도를 아예 내리고 사유를 화면에 적는다.
  일부만 칠해진 지도는 빈 곳이 '예산 0' 으로 읽혀 없느니만 못하다
